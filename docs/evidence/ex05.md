## Failed check and evidence

Date recorded: 2026-10-11. **Simulated output, supplied by the course:**

```
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

The zone still contains the old Azure record: `site.lab.example. 300 IN A 198.51.100.24`.

## Diagnosis

**DNS to the destination:** `dig` returns an A record to `198.51.100.24`, which is the old Azure VM. It is not the Railway target. So the name still sends traffic to the old server, and Railway never sees the request.

**TLS to the certificate:** curl confirms it connected to `198.51.100.24`, the same address DNS gave. That server presents its own certificate, `CN=old-vm.lab.example`, which does not cover `site.lab.example`, so curl stops with error 60.

**What the evidence supports:** the root fault is the stale DNS record. The certificate mismatch is a symptom of it: we are talking to the wrong server, so we get the wrong certificate. The observation that supports this is that the connected IP in curl matches the old A record in dig.

**What remains uncertain:**

- Whether Railway will issue a valid certificate for `site.lab.example` once traffic reaches it. Nothing above tests Railway's TLS.
- Whether the page and database content load over the custom domain. A correct DNS answer alone does not prove that.
- With a 300 second TTL, some resolvers may keep returning the old A record for up to five minutes after the change.

**Proposed repair:**

1. In Cloudflare, delete the A record `site → 198.51.100.24`.
2. Add `CNAME site → current-app.up.railway.app`, DNS only.
3. Confirm `site.lab.example` is attached as a custom domain in Railway, so Railway issues a certificate for it.
4. After the TTL passes, rerun the same `dig` and `curl -Iv`.

**Comparison:**

| | Before | After |
|---|---|---|
| DNS answer | `A 198.51.100.24` (old Azure VM) | `CNAME current-app.up.railway.app`, which resolves to `A 203.0.113.44` |
| Connected address | `198.51.100.24` | `203.0.113.44` |
| Certificate name | `CN=old-vm.lab.example` (mismatch) | `CN=site.lab.example` (verify ok) |
| HTTP result | none, curl stopped at error 60 | `HTTP/2 200` |

**The record change:** the A record pointing at the old VM was replaced with a CNAME to the Railway target. That is the same change I proposed.

**Which fault came first:** the DNS fault. The stale A record sent clients to the old server, and the certificate mismatch only happened because of that. Once DNS changed, the connection went to Railway, and with no TLS change at all the certificate matched. That shows the TLS error was a symptom of the DNS fault, not a separate problem.

**Does it support my diagnosis:** yes. I don't need to revise it. The one uncertainty I listed, whether Railway would issue a certificate for `site.lab.example`, is answered: it did.

**What this still doesn't prove:** `HTTP/2 200` only shows the server answered. It does not show the page has the current content from the database. I would check that by loading the page and comparing it with the Railway URL. In a real cutover I would also query more than one resolver, because some could still return the old A record until the 300 second TTL runs out.

## What you learned

One check that separates a DNS problem from a TLS or application problem is to skip DNS and force curl to the correct server:

```
curl -Iv --resolve site.lab.example:443:<railway-ip> https://site.lab.example/
```

If that succeeds while the normal `curl` fails, the problem is DNS. If it still fails with a certificate error, the problem is TLS on Railway's side. If TLS passes but the page or data is wrong, the problem is the application.

Another check is to query different public resolvers, such as `dig @1.1.1.1` and `dig @8.8.8.8`. If they disagree, the change is still propagating and I should wait and repeat the check rather than change more records.

If the failure had remained after the record change, I would check next:

- whether the old A record was actually deleted, or whether an A record and the CNAME both still existed
- whether the Cloudflare record had been switched to proxied by mistake, which would put Cloudflare's certificate in front of Railway
- whether the custom domain shows as verified in Railway and has a certificate issued
